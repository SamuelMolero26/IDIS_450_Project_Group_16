3.2 Stage 2: Data Quality Assurance

**Architecture Overview:**
```
[Stage 1 DataFrame]
         ↓
[Missing Value Handler]
    ├── Numerical: Median Imputation
    ├── Categorical: Mode Imputation
    └── Temporal: Forward Fill
         ↓
[Consistency Validator]
    ├── Date Logic: Procured ≤ Order ≤ Ship ≤ Delivery
    ├── Value Ranges: Cost/Price/Quantity > 0
    └── Discount Bounds: 0.0 ≤ Discount ≤ 1.0
         ↓
[Duplicate Remover]
         ↓
[Stage 2 Output: Quality-Assured DataFrame]
```

**Detailed Implementation:**

**Step 2.1: Missing Value Strategy Selection**
- Analysis: 0.01% missing data detected (8/7,991 records)
- Strategy: Smart imputation based on feature type
  - Numerical: Median (robust to outliers)
  - Categorical: Mode (preserves distribution)
  - Temporal: Forward fill (maintains sequence)
- Decision Rationale: Minimal data loss, distribution preservation
- Benefit: Maintains statistical properties without introducing bias

**Step 2.2: Date Logic Validation**
- Validation Rules:
  - ProcuredDate ≤ OrderDate (procurement before ordering)
  - OrderDate ≤ ShipDate (order before shipping)
  - ShipDate ≤ DeliveryDate (shipping before delivery)
- Error Handling: Flag violations, log for review
- Decision Rationale: Business rule enforcement
- Benefit: Prevents impossible temporal sequences

**Step 2.3: Value Range Validation**
- Numerical Constraints:
  - Order_Quantity > 0 (no negative orders)
  - Unit_Cost > 0 and Unit_Price > 0 (no free/negative pricing)
  - Discount_Applied ∈ [0,1] (percentage bounds)
- Outlier Flagging: Values outside 3σ bounds logged
- Decision Rationale: Domain knowledge application
- Benefit: Eliminates nonsensical business data

**Step 2.4: Duplicate Detection and Removal**
- Method: df.duplicated().sum() across all columns
- Result: 0 duplicates found
- Decision Rationale: Exact matching preserves data integrity
- Benefit: Ensures unique transaction records

**Performance Impact:**
- Execution Time: ~1 second
- Data Loss: 0.01% (minimal)
- Quality Improvement: 100% consistency score

**Business Value:**
- Reliable data foundation for analytics
- Compliance with business rules
- Prevention of downstream model errors

3.3 Stage 3: Feature Engineering

**Architecture Overview:**
```
[Quality DataFrame (7,991 × 16)]
         ↓
[Temporal Feature Engineer]
    ├── Procurement_to_Order_Days
    ├── Order_to_Ship_Days
    ├── Ship_to_Delivery_Days
    └── Total_Lead_Time
         ↓
[Financial Feature Engineer]
    ├── Profit_Margin = ((Price×(1-Discount)) - Cost) / Cost
    └── Total_Revenue = Quantity × Price × (1-Discount)
         ↓
[Interaction Feature Engineer]
    ├── Price_Quantity_Interaction
    ├── Cost_Quantity_Interaction
    ├── Discount_Price_Interaction
    ├── Margin_Quantity_Interaction
    ├── LeadTime_Quantity_Interaction
    ├── Price_Cost_Ratio
    └── Discount_Margin_Interaction
         ↓
[Stage 3 Output: Enriched DataFrame (7,991 × 29)]
```

**Detailed Implementation:**

**Step 3.1: Temporal Feature Creation**
- Calculations:
  - Procurement_to_Order_Days = OrderDate - ProcuredDate
  - Order_to_Ship_Days = ShipDate - OrderDate
  - Ship_to_Delivery_Days = DeliveryDate - ShipDate
  - Total_Lead_Time = DeliveryDate - ProcuredDate
- Data Type: Convert to numeric (days)
- Decision Rationale: Operational efficiency metrics
- Benefit: Quantifies supply chain performance

**Step 3.2: Financial Feature Engineering**
- Profit_Margin Formula: ((Unit_Price × (1 - Discount_Applied)) - Unit_Cost) / Unit_Cost
- Total_Revenue Formula: Order_Quantity × Unit_Price × (1 - Discount_Applied)
- Decision Rationale: Business-critical financial ratios
- Benefit: Direct revenue and profitability insights

**Step 3.3: Interaction Feature Design**
- Rationale: Sales data exhibits multiplicative relationships
- Examples:
  - Price_Quantity_Interaction = Unit_Price × Order_Quantity
  - Discount_Price_Interaction = Discount_Applied × Unit_Price
  - Price_Cost_Ratio = Unit_Price / Unit_Cost
- Decision Rationale: Captures non-linear business dynamics
- Benefit: Enables complex pattern recognition by ML models

**Step 3.4: Feature Validation**
- Correlation Checks: Ensure new features correlate with target
- Multicollinearity Assessment: VIF analysis for redundancy
- Business Logic Validation: Domain expert review
- Decision Rationale: Quality assurance for engineered features
- Benefit: Prevents inclusion of spurious features

**Performance Impact:**
- Execution Time: ~3 seconds
- Feature Growth: 16 → 29 features (+81%)
- Memory Increase: ~150MB additional
- Computational Cost: Vectorized operations

**Business Value:**
- Enhanced predictive power through domain knowledge
- Actionable operational insights

```
[Contextual Outlier Analysis]

    └── Temporal Pattern Validation
         ↓
[Outlier Treatment Engine]
    ├── Removal Strategy: Delete flagged records
    └── Preservation Logic: Business rule validation
         ↓
[Stage 4 Output: Clean DataFrame (7,947 × 29)]
```

**Detailed Implementation:**

**Step 4.1: Univariate Outlier Detection**
- Z-Score Method: (x - μ) / σ > 4 threshold
- IQR Method: Q3 + 3×IQR (aggressive outlier removal)
- Features Analyzed: All numerical (focus on Total_Revenue, Unit_Price)
- Decision Rationale: Statistical rigor with business context
- Benefit: Removes extreme values that could skew model training

**Step 4.2: Multivariate Outlier Detection**
- Isolation Forest: Tree-based anomaly detection, contamination=0.05
- Local Outlier Factor: Distance-based method, n_neighbors=20
- Decision Rationale: Captures anomalous combinations
- Benefit: Identifies outliers not visible in single dimensions

**Step 4.3: Contextual Analysis**
- Channel-Specific: Different thresholds for Wholesale vs Retail
- Temporal Patterns: Seasonal outlier validation
- Business Rules: Flag but preserve legitimate bulk orders
- Decision Rationale: Domain-aware outlier handling
- Benefit: Preserves business-critical extreme values

**Step 4.4: Treatment Strategy**
- Removal Rate: 4.3% (44 outliers from 7,991)
- Selective Preservation: Keep channel-specific extremes
- Decision Rationale: Balance between data quality and business relevance
- Benefit: Improved model stability without losing important patterns

3.5 Stage 5: Standardization & Encoding

**Architecture Overview:**
```
[Clean DataFrame (7,947 × 29)]
         ↓
[Categorical Encoder]
    ├── OneHotEncoder: drop='first'
    └── Feature Mapping: Sales_Channel → 3 dummies
         ↓
[Numerical Scaler]
    ├── RobustScaler: median-based, IQR normalization
    └── Feature Preservation: Maintains distribution shape
         ↓
[Feature Balance Assessor]
    ├── Skewness Analysis: |skew| > 2 flags
    └── Distribution Validation: Normality tests
         ↓
[Stage 5 Output: ML-Ready DataFrame (7,947 × 25)]
```

**Detailed Implementation:**

**Step 5.1: Categorical Encoding Strategy**
- Method: OneHotEncoder with drop='first' to prevent multicollinearity
- Target Features: Sales_Channel (4 → 3 dummies), WarehouseCode, CurrencyCode
- Decision Rationale: Avoids dummy variable trap, enables linear model compatibility
- Benefit: Proper categorical representation for ML algorithms

**Step 5.2: Numerical Scaling Selection**
- Scaler Choice: RobustScaler (median, IQR) over StandardScaler (mean, std)
- Reason: Resistant to outliers, preserves feature relationships
- Formula: (x - median) / IQR
- Decision Rationale: Handles sales data outliers (bulk orders)
- Benefit: Improved convergence for gradient-based algorithms

**Step 5.3: Feature Balance Assessment**
- Skewness Threshold: |skewness| > 2 requires transformation consideration
- Distribution Tests: Shapiro-Wilk for normality
- Balance Metrics: Feature variance ratios
- Decision Rationale: Identifies features needing special handling
- Benefit: Guides model selection and feature engineering

**Step 5.4: Dimensionality Optimization**
- Feature Selection: Remove CurrencyCode (100% USD, no variance)
- Identifier Removal: Drop _SalesTeamID, _CustomerID, _StoreID, _ProductID
- Decision Rationale: Eliminates non-predictive features
- Benefit: Reduces noise, improves computational efficiency

**Performance Impact:**
- Execution Time: ~2 seconds
- Feature Reduction: 29 → 25 features (-14%)
- Encoding Overhead: 3 additional dummy variables
- Memory Efficiency: Optimized for ML training

**Business Value:**
- Algorithm compatibility across model types
